# Design

## Context

See `proposal.md` for the motivation and scope. Cairn is a Nuxt 4 application using Vue, Tailwind CSS v4, Vue Flow, CodeMirror, Vitest, Vite+, and GitHub Actions. SonarCloud currently analyzes source and test paths, while the test workflow does not produce an LCOV report for the scan. Existing graph/editor UI includes domain-specific interaction that should remain owned by Cairn.

## Goals / Non-Goals

**Goals:**

- Migrate suitable generic controls to Nuxt UI before addressing Sonar findings.
- Make test coverage generated by CI available to the SonarCloud analysis.
- Reduce reported complexity and maintainability findings in behavior-preserving changes.
- Keep each refactor protected by focused tests and document any changed developer workflow.

**Non-Goals:**

- Change product behavior or redesign the graph editor.
- Migrate Vue Flow, CodeMirror, or Cairn-specific graph nodes to Nuxt UI.
- Suppress Sonar findings by broad exclusions or rule downgrades.
- Enforce a global coverage threshold unrelated to Sonar's new-code quality gate.

## Decisions

### Migrate generic controls to Nuxt UI first

Adopt the Nuxt UI version compatible with this Nuxt 4 and Tailwind CSS v4 setup. First identify generic controls already represented by Nuxt UI (buttons, form inputs, selects, accordions, menus, and toast/notification primitives). Migrate one cohesive surface at a time, preserving Cairn's visual tokens and interaction semantics, and cover each migration with component tests. Keep Vue Flow graph nodes/canvas and the CodeMirror request editor as domain-specific components.

This is the first implementation phase so subsequent Sonar remediation applies to the resulting component structure. Incremental migration limits layout and interaction regressions and makes the library's behavior and keyboard accessibility verifiable before broader adoption. Replacing all markup at once or wrapping every library component in a new abstraction would add risk and recreate the custom-component maintenance burden.

### Generate LCOV after the UI migration

Once the UI migration is complete, configure Vitest/Vite+ coverage using a provider compatible with the installed toolchain and emit `coverage/lcov.info`. The CI job should run the relevant test suites with coverage before invoking SonarCloud analysis. Configure the scanner to consume that exact LCOV path and preserve current source/test exclusions. Keep coverage artifacts available long enough for the scanner job; prefer a single job when practical, or upload/download the report explicitly when jobs are separated.

This keeps the report reproducible from the same tests used in CI and measures the code state after the UI migration. A separately generated or locally uploaded report could become stale or fail to represent the analyzed commit.

### Address Sonar findings after migration and coverage wiring

Use the current SonarCloud issue list as a starting inventory, then re-query issues after UI migration because findings can change. Prioritize the seven reported complexity hotspots (OpenAPI/Postman import, mock API view models, and OTLP ingestion), followed by repeated maintainability and accessibility rules. Preserve behavior and add or update focused tests in the same batch. For sequential awaits, retain ordering where operations depend on earlier results; do not mechanically parallelize. Remove `!important` only when the cascade remains correct, and use semantic controls/keyboard interactions for accessibility findings.

This favors evidence-based fixes over bulk rule suppression or cosmetic edits that could change runtime behavior.

### Keep verification close to each change

Each refactor batch includes focused tests and any documentation updates it requires. The final integration pass runs the project check/build and the full CI test-and-coverage path, then confirms SonarCloud receives the report and updates the quality gate. Do not make CI depend on an unavailable Sonar secret in pull-request contexts; retain the repository's existing secret and fork behavior.

## Risks / Trade-offs

- [Nuxt UI defaults alter spacing, focus, or dark-mode appearance] → Migrate incrementally and assert key behavior and rendered states in component tests.
- [Coverage provider or Vite+ integration differs from the current installed versions] → Inspect the installed toolchain after UI migration, choose its supported provider, and verify the generated LCOV locally before changing CI.
- [Coverage remains below the 80% new-code gate after report ingestion] → Use the gate's measured new-code scope to add focused tests to changed code; do not inflate coverage with unrelated tests.
- [Sonar findings are stale or resolved by adjacent changes] → Refresh issue data after migration and update the remediation tasks based on current findings.
- [Simplifying sequential async logic changes ordering] → Preserve dependency order and add tests for the relevant success/failure paths.

## Migration Plan

1. Add/configure Nuxt UI and migrate generic controls by surface, checking component behavior and theme/accessibility states after each batch.
2. Configure local coverage generation and scanner report path; validate LCOV exists and is readable.
3. Update CI ordering/artifact transfer so analysis runs only after coverage is available; keep existing secret handling.
4. Refresh SonarCloud issues, then fix complexity and recurring findings in focused batches, with tests and documentation alongside each batch.
5. Run full checks, tests, build, and the CI-equivalent coverage scan; inspect the resulting Sonar issues and quality gate.

Rollback by reverting an individual Nuxt UI, CI, or refactor batch. Coverage setup can be removed independently; it does not alter persisted data or APIs.

### Sequential operations retained

Reviewing the current sequential-await findings confirmed they are order-sensitive: run-flow polling must observe the preceding response before waiting; canvas, service, and span mutations run through one MySQL transaction; and mock API/variable saves stop on the first failed write while updating local IDs after successful creates. These remain sequential to preserve their error and partial-save semantics. Telemetry ingestion tests assert project lookup and persistence ordering, and mock API view-model tests assert save request order.

### Accessibility and CSS remediation

The accessibility findings were handled in the current source by using native dialog elements with Escape dismissal, giving the Postman file picker an accessible name, grouping the CodeMirror request editor with its visible label, using a native `<hr>` for the keyboard-operable log panel resize separator, and using `<output>` for warning and service status output. The context menu now delegates outside-dismiss behavior to Nuxt UI instead of click handlers on the page and canvas. Framework selection is now Nuxt UI's native select primitive; the old custom combobox findings refer to removed markup. Tests cover dialog Escape behavior, resize keyboard behavior, and service status semantics.

Vue Flow style overrides now use scoped selector specificity instead of `!important`. CSS imports are ordered before `@reference`; obsolete commented CSS was removed; `word-break: break-word` was changed to `overflow-wrap: anywhere`. The CodeMirror placeholder background is now an opaque color matched to the light and dark editor surfaces, preserving its rendered appearance while making the contrast explicit to static analysis.
