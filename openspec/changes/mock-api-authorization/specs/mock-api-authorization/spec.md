# Spec Delta

## Purpose

This capability provides reusable authorization configurations for Cairn mock API calls, including static credentials and OAuth client-credentials access tokens.

## ADDED Requirements

### Requirement: Manage shareable authorization templates

Cairn SHALL let an operator create, edit, and delete named project-scoped authorization templates in Mock APIs settings.

#### Scenario: Add an authorization template

- **WHEN** the operator selects New template
- **THEN** Cairn adds an expanded template accordion with a name field and an authorization type selector
- **AND** the operator can save or discard the template with the Mock APIs settings

#### Scenario: Reject duplicate template names

- **WHEN** the operator saves templates with duplicate names in the project
- **THEN** Cairn rejects the save and identifies the duplicate without partially saving the settings

### Requirement: Configure authorization fields by type

Cairn SHALL display and validate only the fields required by the selected authorization type.

#### Scenario: Select a static authorization type

- **WHEN** the operator selects Bearer token, Basic Auth, or API key
- **THEN** Cairn shows the corresponding token, username/password, or header key/value fields

#### Scenario: Select OAuth client credentials

- **WHEN** the operator selects OAuth 2.0 Client Credentials
- **THEN** Cairn shows token URL, client ID, client secret, and optional scope fields
- **AND** Cairn does not offer Authorization Code or other OAuth grant types

### Requirement: Assign an authorization template to a mock API

Each mock API SHALL use either No Auth or one saved project authorization template.

#### Scenario: Select a saved template

- **WHEN** an operator selects a saved authorization template in an API's Authorization accordion and saves settings
- **THEN** Cairn uses that template for subsequent runs of that API

#### Scenario: Use no authorization

- **WHEN** an API has no selected authorization template
- **THEN** Cairn sends no authorization data generated by an authorization template
- **AND** existing APIs without a template continue to run under their existing header configuration

#### Scenario: Update a shared template

- **WHEN** an operator saves changes to a template used by multiple APIs
- **THEN** subsequent runs of every referencing API use the updated template

### Requirement: Apply static authorization at request time

Cairn SHALL generate the appropriate outbound request credential from the selected static authorization template.

#### Scenario: Apply a bearer token

- **WHEN** an API uses a Bearer token template with a valid token value
- **THEN** Cairn sends `Authorization: Bearer <token>` to the target API

#### Scenario: Apply Basic Auth

- **WHEN** an API uses a Basic Auth template with a valid username and password
- **THEN** Cairn sends the corresponding HTTP Basic Authorization header to the target API

#### Scenario: Apply an API key

- **WHEN** an API uses an API key template
- **THEN** Cairn sends the configured key/value as a request header using the configured header name

### Requirement: Acquire OAuth client-credentials tokens

Cairn SHALL obtain and use OAuth access tokens with the Client Credentials grant for APIs assigned an OAuth template.

#### Scenario: Obtain and use an OAuth token

- **WHEN** an API run needs an uncached or expired OAuth access token
- **THEN** Cairn requests a token from the configured HTTP(S) token URL using `grant_type=client_credentials`, the configured client credentials, and optional scope
- **AND** Cairn sends the returned access token as a Bearer Authorization header to the target API

#### Scenario: Reuse an unexpired OAuth token

- **WHEN** another run uses the same unchanged OAuth template before its access token expires
- **THEN** Cairn reuses the cached access token until shortly before expiry

#### Scenario: OAuth token acquisition fails

- **WHEN** the token endpoint fails or returns an invalid token response
- **THEN** Cairn fails the run without sending the target API request
- **AND** Cairn does not expose the client secret or access token in logs or user-facing errors

### Requirement: Reject authorization header conflicts

Cairn SHALL reject a mock API configuration when a raw header template or custom header defines a name generated by its selected authorization template.

#### Scenario: Authorization header conflicts

- **WHEN** an API selects Bearer, Basic Auth, or OAuth and its effective raw headers also define `Authorization` using any letter case
- **THEN** Cairn marks the API as not ready and does not send an outbound request
- **AND** the readiness reason identifies the conflicting header name without revealing its value

#### Scenario: API key header conflicts

- **WHEN** an API key template's configured header name duplicates a raw header template or custom header name case-insensitively
- **THEN** Cairn marks the API as not ready and does not send an outbound request

#### Scenario: Non-conflicting headers remain available

- **WHEN** an API has a selected authorization template and its raw headers do not define any generated authorization header name
- **THEN** Cairn sends both the generated authorization and the remaining effective raw headers

### Requirement: Protect authorization values in the settings interface

Cairn SHALL visually mask secret credential fields by default and SHALL avoid including credential values in readiness messages or request failure logs.

#### Scenario: Reveal a secret while editing

- **WHEN** an operator activates the visibility control for a secret field
- **THEN** Cairn shows that field's value until the operator hides it again or closes the settings panel
